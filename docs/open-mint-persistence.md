# Open-mint persistence foundation

Status: local E17 implementation increment, **not complete E17 and not a public runtime**. Nothing in this module is wired into the active file-backed service or its wallet-session map. The explicit assessment worker can invoke server-injected generation adapters only for an already admitted private request; all validation uses mocked transports, with no paid/provider calls made during this work. It signs no mint authorization, applies no migration at startup, imports no existing records, and enables no public profile. See [public architecture](public-architecture.md) for the remaining integration and operating decisions.

## Implemented boundaries

- `src/openMint/persistence/schema.sql` is an additive, transactional, apply-once migration creating the separate `open_mint` schema. It does not touch legacy/public tables or local pilot files. Namespace-qualified foreign keys, canonical-handle uniqueness, one initial attempt, immutable reservation/receipt/identity/assessment evidence, and monotonic job/challenge/session transitions are database constraints. A second application of this initial migration fails without changing an existing schema; a versioned migration runner and upgrade/rollback rehearsal remain future work.
- `ExclusiveWriter` takes a fresh dedicated PostgreSQL client, immediately refuses a competing session advisory lock, validates schema version 1, and commits a monotonically increasing writer epoch. Every transaction runs serially on that same connection and verifies the epoch, its actual advisory lock, and durable commit settings. PostgreSQL `fsync` must be on; the session forces `synchronous_commit=on`, preserving an existing `remote_apply` setting. Statement/idle-transaction timeouts are five seconds; lock timeout is one second. The factory must also configure a bounded connection-establishment deadline.
- Connection error/end, missing ownership, unsafe durability settings, failed rollback, and an ambiguous commit permanently invalidate that writer object. It neither reconnects nor retries automatically. No transaction result escapes after a lost commit acknowledgment. Graceful close rejects new/queued transactions and waits for the active transaction to finish or roll back before closing its owner session. Already-started external work cannot be cancelled by a PostgreSQL lock.
- `OpenMintRepository.admitInitial` locks policy, then a permanent canonical handle guard. It atomically creates the initial attempt, UTC-day reservation, and unique assessment job, or joins existing work/reuses the validated accepted result. This lower-level API deliberately does **not** authenticate an HTTP request. The new `PostgresMintRequests` composes it with session ownership and trusted chain preflight inside the same transaction; active handlers must use that composed boundary when integration is approved.
- Initial job claiming, a separate committed marker for each provider leg, immutable allowlisted receipts, validated X identity, and accepted-result insertion form explicit stages. Grok dispatch requires a successful durable X receipt and matching validated identity. The accepted result must match the namespace/policy/model, attempt handle, stored identity, successful Grok receipt, and any receipt response/model identifiers. The exact accepted UTF-8 bytes, accepted attempt transition, completed assessment job, and next render job commit atomically. Exact identical insertion is idempotent; conflicting bytes are rejected.
- The policy bounds initial attempts, daily attempts, active attempts (one), queued work (at most 100), and integer USD exposure ticks. Policy fields are immutable except their kill switch. The generation switch, expiry, positive real reservation, model/provenance, and exposure are rechecked before each provider fence. Unknown/estimated final accounting blocks another **real** admission; saved-result reuse remains available. There is no accounting reconciliation/release API in this increment.

Exposure intentionally never decreases: each reservation contributes at least its original reserved amount, or the larger sum of recorded actual/estimated costs. UTC day rollover resets only the daily count; it does not erase total history, reservations, or uncertainty. This is conservative capacity accounting, not a dollar-bill guarantee. A later reviewed reconciliation record must preserve original receipts and explain any change in available allowance.

A replacement writer may claim an untouched queued job after its caller independently revalidates authority and policy. A job already marked running cannot be reclaimed, even before its first provider marker. A dispatched leg cannot be dispatched again. A verified identity without a Grok marker does not enable automatic continuation after restart. Interrupted work remains blocked for a future explicit recovery policy; this module is not a background worker.

## Durable wallet sessions

`PostgresWalletSessions` is an asynchronous companion to the existing `WalletSessions`, with a separately provisioned immutable namespace/origin/chain profile. It preserves the 24-hour session lifetime, ten-minute challenge/proof lifetime, exact wallet-signing statement/resource semantics, canonical EOA verification, exact Origin/CSRF policy, cookie flags, one active challenge, and the 10,000-live-session ceiling. It is not a synchronous drop-in replacement.

Session tokens and challenge IDs are looked up only by SHA-256 hash. Request scope in the saved proof is `codeHash`, not a recoverable request code. Cookie recovery uses the original token supplied by the browser; no digest becomes a new capability. The CSRF material is private session data and remains recoverable for that authenticated browser.

Challenge consumption commits **before** asynchronous signature verification. Invalid signatures leave the challenge consumed. Proof persistence re-locks the session and requires the unchanged generation, live nonrevoked session, no replacement challenge, and the original unexpired challenge context. Logout and challenge replacement increment generation and invalidate prior proof. The final persistence acknowledgment is required before verification returns success. Pending challenges, proof scope, CSRF, and logout survive writer/process replacement.

The exact signed message is stored privately as bounded UTF-8 `bytea`. Under the existing signing semantics, a request-scoped message contains its raw private request URL/code; hashing the lookup columns does **not** remove that capability from the signed-message evidence. Challenge messages, CSRF values, and session proofs must stay out of logs, diagnostics, public projections, backups without access controls, and analytics. Encrypting this evidence at rest with reviewed custody, if required by the public operating policy, remains an integration decision; the implementation does not silently change the signed resource.

Callers must replace raw proof-code comparisons with hash comparisons, await session operations, and stop passing mutable in-memory `SiteSession` objects as durable authority. A stale returned snapshot is not authorization. Request admission and authority issuance must revalidate current session generation/proof **inside their own database transaction**, not rely on a separate earlier `authorizePost` or session read. The HTTP method/Origin/CSRF gate remains required before invoking session mutations, as with the current local adapter. The composed request creator includes its own transactional Origin/CSRF gate. No current server route has been changed to use these methods.

## Atomic private request admission

`requests-schema.sql` is a separate additive migration after `schema.sql`. An immutable request profile binds a deployment UUID to namespace, chain ID, contract, genesis, runtime-code hash, authorizer, deployment block/hash, and bounded evidence-age/block-age/future-skew policy. The session profile's chain must agree. Multiple deployment profiles can share one assessment namespace without giving a canonical handle another initial assessment.

`PostgresMintRequests.create` receives the original session token, exact Origin/CSRF, captured wallet and session generation, handle spelling, and an opaque backend chain witness. The caller obtains chain preflight before entering this transaction. The real `PublicChainGate` accessor authenticates the witness using its process-local WeakMap: a boolean, serialized object, or caller-authored JSON observation is rejected. Admission compares all chain identity and freshness pins against the immutable database profile, so even an authentic witness from a gate configured with the wrong runtime or looser freshness policy cannot pass.

In one transaction, creation locks and checks the live session, exact Origin/CSRF, unchanged captured wallet/generation, and fresh **general** wallet proof; checks the witness and ten-live-requests-per-session limit; admits/joins/reuses the canonical assessment work; and inserts a private request. It checks proof/session expiry and witness freshness again after the writes. Delays that make either stale roll back the request, attempt, reservation, and job together. No RPC, provider, or wallet call occurs inside this transaction.

Requests preserve the original case spelling, canonical handle, recipient, admission generation, original attempt or accepted-assessment link, and an exact fifteen-minute lifetime. Their chain block/hash/nonce observation is private audit context, **not** a nonce/authority reservation. Records cannot be rewritten or deleted by the runtime. A pending request can observe its canonical assessment later through a validated join without changing its frozen admission record. `assessment-accepted` does not mean rendered, published, signed, or ready to mint.

Only the SHA-256 request-code hash is persisted. Each new explicit creation returns a fresh random code and can join the same single initial job; duplicate creations consume separate bounded request slots, not another assessment. The database cannot reconstruct an earlier raw code. Existing reads require the browser's original code and live owning session with the same wallet. Expired requests remain privately readable without extending their expiry, creating a session, starting work, or returning authority. Returning to mint can create a new request for an existing accepted result even while new generation is disabled, provided the fresh proof and chain gates pass.

The saved request generation is an admission audit value, not a permanent ban on later reconnecting the same wallet. A later authority transaction must validate the current general/request-scoped proof and capture the **current** generation; signer completion must then match that captured generation. Requiring the original request generation after a request-scoped challenge would invalidate the very reconnect operation that the existing local recovery flow permits.

## Explicit assessment execution

`PostgresAssessmentWorker.run` is a separate, local-profile-only backend operation, not a queue pump or an HTTP handler. There is no handle-only admission shortcut or automatic retry. It requires an existing private request code, its owning cookie, current wallet generation, Origin/CSRF, live general or matching request-scoped proof, and a fresh opaque chain witness. In the same transaction as initial job claiming, it locks and checks current request/session state and the full immutable chain/freshness profile before and after the write. Accepted results can be returned without generation adapters or an enabled generation policy; saved work never triggers another call.

Every explicit execution constructs a fresh `AssessmentCoordinator`, preventing another run's in-memory cache or unsaved retry from skipping durable dispatch checks. Before each X/Grok leg, a server-owned callback obtains a new opaque chain witness outside the transaction. Current request/session/proof/generation/Origin/CSRF, chain eligibility, policy and exposure are rechecked in the same transaction as the unique dispatch marker. No provider, chain or wallet I/O runs inside that transaction. Only successful commit acknowledgment permits the corresponding transport, with another local owner/deadline check immediately before invocation.

Allowlisted receipts commit before semantic acceptance; validated X identity commits before Grok. Exact assessment bytes, accepted linkage and the render job remain one transaction. Logout after a provider response does not erase a paid fact: accepted evidence is retained, but release to that stale session fails. The worker's full assessment result is private backend data, not a progress-response projection or public metadata.

An explicit server-configured whole-run deadline of 1–180,000 ms uses both a timer and monotonic elapsed checks. Timeout aborts the preflight callback signal and immediately closes all execution callbacks. Guards run **inside** queued receipt/identity/result/outcome transactions, before queries and before returning to commit; late callbacks cannot persist or start another leg. Existing generation transports retain their own request/body deadlines. A non-cooperative remote transport cannot be physically undone; its marker and reservation remain. Cleanup waits only for the bounded database claim acknowledgment, then derives phase from durable fences and closes only this run's acknowledged, current-epoch running attempt. It never closes another concurrent claim, a queued job, a saved acceptance, or an operation with a lost writer/commit acknowledgment. Database cleanup may add bounded statement/lock-timeout latency beyond the external-work deadline.

`assessment_terminals` stores only an immutable bounded kind, abstention reason where applicable, last committed dispatch phase, owner epoch and database timestamp. A successful Grok receipt is required before recording abstention. Semantic-invalid requires a durable successful response plus a validated semantic failure; typed Grok/X failures are distinguished from body/HTTP/transport/storage errors. `uncertain` means a dispatched pipeline has no accepted result, not proof that no charge occurred. `blocked-before-dispatch` is permitted only with zero durable dispatch markers. Terminal insertion, guarded attempt `pending → closed`, and assessment job completion are atomic. This frees the active slot only: the permanent handle guard, one-attempt limit, reservations, receipts and exposure never reset. Missing/estimated accounting still blocks another real admission. Reads and duplicate private requests show bounded terminal status rather than pretending failed work is still pending.

Receipt, identity, terminal-outcome or result persistence failure does not fabricate replacement evidence. The job remains claimed/interrupted when those writes did not become acknowledged; an abstention is never relabeled invalid because its storage failed. Already claimed or dispatched jobs cannot be reclaimed after restart. Reviewed operator reconciliation, not another user request, is required for uncertainty.

## Migration and runtime-role boundary

Use a reviewed migration owner to apply this schema, provision immutable namespace/session profiles, and insert reviewed bounded budget policy with generation disabled initially. Supply runtime access using a distinct role that does not own the schema/tables/functions, cannot change triggers, cannot truncate tables, cannot migrate, and cannot access another environment's database. `PUBLIC` receives no schema/table/function privileges from this migration. No roles, passwords, accounts, or grants are provisioned automatically.

The runtime needs schema usage, reads on its tables, inserts on the evidence/operational tables used by its repository, updates on the writer epoch and the explicitly implemented attempt/job/session/challenge transitions. Policy enablement belongs to a separately reviewed operator path. Do not grant blanket `ALL`, ownership, `TRUNCATE`, or migration privileges. Namespace-qualified repository queries and foreign keys prevent accidental cross-environment links; they are not PostgreSQL row-level security against arbitrary SQL by a compromised runtime role. Use separate databases/credentials for staging and production, as proposed in the architecture.

Most tests use a disposable cluster owner to inject faults and seed historical states. `runtimeRole.ts` separately provides a foundation-only SQL grant template, without creating a role or connecting to a database. It names each existing table and permitted update column; it does not grant ownership, schema creation, deletes, truncation, grant options, future-table access, or permission to change the generation switch/budget bounds. PostgreSQL row locks require an update privilege, so policy/handle locks receive only an immutable key-column grant, still protected by triggers.

`runtimeRole.test.ts` authenticates directly as a nonsuperuser in a disposable private Unix-socket cluster. It completes repository acceptance and wallet-session transitions, then verifies that policy/profile mutation, evidence deletion/truncation, trigger disabling, and DDL are denied. An unrelated role cannot read private records. These tests cover the foundation only: request, publication, issuance and projection grants, inherited role membership, hosting-specific privileges, and startup checks still need public integration review. The template does not revoke pre-existing excessive privileges or establish database/role isolation. `synchronous_commit=on` does not make an asynchronous replica a safe automatic failover target.

## Verification

Run ordinary mocked/fault boundary tests with:

```sh
npx vitest run src/openMint/persistence/writer.test.ts src/openMint/persistence/repository.test.ts src/openMint/persistence/sessions.test.ts src/openMint/persistence/requests.test.ts src/openMint/persistence/assessmentWorker.test.ts
```

Run actual transactions and constraints with installed PostgreSQL binaries:

```sh
OPEN_MINT_TEST_POSTGRES=1 npx vitest run src/openMint/persistence
```

The test helper creates a new `mkdtemp` directory under `/tmp`, runs `initdb`, starts PostgreSQL with TCP disabled and a private Unix socket, applies only this task's schemas, then stops and removes that exact disposable cluster. It cannot accept a database URL or an existing data directory. `OPEN_MINT_TEST_POSTGRES_BIN` can identify an installed binary directory. It never reads `.env.local`, connects to an application database, or uses a provider/chain transport. The opt-in PostgreSQL suites are skipped without `OPEN_MINT_TEST_POSTGRES=1`; a skipped suite is not transaction evidence.

The September 20 local run verified duplicate/concurrent admission, rollback at job/result/request write boundaries, real-accounting gates, previous-day exposure, immutable conflicts, second-writer refusal, job restart fences, actual backend termination, unsafe-client commit-mode repair, hashed-session continuity, concurrent challenge consumption, wrong-wallet proofs, logout/replacement races, and immutable session-profile protection. Private-request tests cover the live-session cap, general-versus-scoped proof, wrong generation/CSRF/origin, forged and wrongly configured real gate witnesses, accepted-result reuse, restart/read ownership, and a PostgreSQL-injected delay expiring a witness after writes but before commit. Mock fault tests additionally exercise lost commit acknowledgments, rollback failure, startup connection loss, unsafe fsync/durability, invalid payloads, proof-finalization failure, and expiry during verification. No paid calls or real pilot state were used.

Worker tests additionally cover concurrent explicit execution, accepted reuse without adapters, per-leg logout/kill-switch/witness rechecks, invalid/abstained/uncertain terminals, permanent spend retention, terminal immutability, receipt/result/outcome failures, restart refusal, hung preflight, queued-claim timeout, late provider callbacks, guarded queued receipt cancellation, monotonic deadline checks, actual X resolver classification with mocked fetch, and ownership loss after a committed dispatch.

`pipeline.postgres.test.ts` composes real wallet-message verification, durable private admission, the worker, public artifact preparation/publication and the [authorization issuer](open-mint-issuance.md). It verifies that corrupt retrieval blocks signing, exact publication enables a real ECDSA signature with a public throwaway test key, and orderly writer replacement preserves the session, original assessment payload bytes, artifact bytes and saved signature with generation disabled and no additional provider/signer invocation. All chain/provider/upload/retrieval transports are mocked. This is local component-composition evidence, not a public deployment, Anvil mint, live Grok assessment or crash-recovery certification.

## Still required for E17

Local reserve-before-signing and frozen-artifact composition are now tested separately; public issuance, expired-reservation replacement/reconciliation and active integration remain unfinished. Also required: bounded render/publication job claiming/completion and crash recovery; reviewed operator reconciliation; pooled validated read-only operation when the writer is unhealthy; retention/backup/restore and upgrade tooling; extension-role/provisioning tests; and explicit active-service/async-session integration. The current public startup refusal and local pilot isolation must remain until those gates are reviewed. Passing the composed local test does not complete E17 or E18's public integration.
